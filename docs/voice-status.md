# Voice implementation and acceptance

Sarvam `saaras:v4` streams partial/final transcripts from mono PCM16 at 16 kHz. `bulbul:v4-flash` with `simran_en_customer` streams English PCM16 responses. The browser requests microphone access only after Start voice. Mute microphone disables audio tracks and sends silence to maintain the connection; silence still counts toward input duration. Stop voice releases microphone tracks and the AudioContext. Speech-start detection stops queued playback, terminates synthesis and aborts the investigation. Detection depends on provider VAD and network delay; no interruption latency target has been demonstrated.

Add `SARVAM_API_KEY` and `VOICE_REQUESTS_ENABLED=true` to the ignored `.env.model`, then run `npm run investigator:start`. Use the built workbench at http://127.0.0.1:3002/; the Vite development proxy is not configured for voice. Log in, select an incident, click Begin conversation and allow the microphone. Ask “What should we check to investigate slow requests?” Watch captions and listen to streamed progress and findings. Speak again while it plays, then click End conversation and verify the browser microphone indicator turns off. View evidence opens findings and the investigation timeline. Use headphones to reduce microphone echo. Groq's existing 60-second cooldown may delay an immediate follow-up; the latest spoken question is queued until the local cooldown expires. Provider failures are not automatically retried.

The new `ws` dependency supplies authenticated provider WebSockets and a server upgrade handler. POST `/sessions/:id/voice-ticket` requires both existing API bearer and session capability. A ticket expires after 30 seconds and is consumed once. `/voice` requires same-host Origin and carries the ticket in a WebSocket subprotocol, without URL credentials. The server never sends provider keys to the browser. TTS accepts a `speak` control and reads the stored validated answer; the client cannot supply arbitrary speech text. No new tables or queues are needed. Audio stays in bounded transient buffers; it is not recorded to disk. Transcripts go through existing redaction before captions/investigation.

Limits per server process: one active voice connection, six connection attempts, ten minutes total PCM input, 8,000 total synthesized characters. Each connection expires after three minutes; each spoken response is capped at 1,200 characters, 30 seconds of provider time and 1.92 MB audio. Provider handshakes time out after ten seconds. Browser playback queue is bounded to 15 seconds; slow consumers close rather than accumulating audio. These limits reset on restart and do not verify account credit balance. Testing is authorized for free signup credits only; no recharge is performed.

The voice timing shown is provider speech end → first synthesized audio received **at the server**, including investigation work. It does not measure audible playback at a listener's ear. Text questions without a new speech endpoint do not establish a voice response latency. Final model answers remain buffered until validation; STT and TTS transport stream.

Validation: local WebSocket tests use explicitly synthetic provider/audio fixtures (Origin and ticket enforcement and expiration, caption redaction, PCM bounds, validated-answer synthesis and cancellation). `npm run test:investigator` passed three real MCP/RAG integration tests with synthetic model fixtures. A live Sarvam synthetic speech loopback generated 3.025 seconds of audio, received 30 partial events and the final transcript “What should we check to investigate slow request?”; report: `eval/reports/voice-provider-smoke.json`. This is provider protocol evidence, not browser microphone acceptance. Browser automation could not initialize on this host (“failed to write kernel assets”); microphone capture, audible playback, browser interruption and microphone release need manual acceptance. No production or latency guarantees are claimed.

Primary API contracts: [realtime transcription](https://docs.sarvam.ai/api-reference/speech-to-text/transcribe/realtime/ws), [streaming synthesis](https://docs.sarvam.ai/api-reference/text-to-speech/stream), [credits and rate limits](https://docs.sarvam.ai/api/getting-started/ratelimits).

The live gateway test (`node --env-file=.env.model --import tsx scripts/voice-smoke.ts --gateway`) also passed: a 2.68125-second synthetic question traversed the authenticated local WebSocket, returned 32 partial captions and a final transcript, triggered Groq plus two real MCP telemetry calls, produced a validated answer and returned 24,200 bytes of synthesized PCM before the test deliberately closed the voice connection. Speech end → first audio at server was 6,457 ms in this single sample. Report: `eval/reports/voice-gateway-smoke.json`. This does not establish typical latency or audible browser playback. The non-hosted unit suite passed 44 tests including five voice tests.

Final `npm run lint`, `npm run typecheck` and `npm run build` passed. A scan of 117 Git-eligible files found zero occurrences of the configured Groq key, Sarvam key or API bearer token. The local investigator container was rebuilt to load the configured key and enabled voice flag; no commit or push was made.

## Conversational interface update

The default screen now centers on a voice conversation, with real listening/thinking/speaking states, mute and End conversation. Begin conversation is clicked once to grant browser microphone access; stable utterances automatically trigger investigation and spoken replies, then listening continues. Typing is an optional collapsed fallback. Findings, timings, source links and tool records live behind View evidence. The orb animates connection/playback states; it is not an audio waveform or measured signal.

The server streams a fixed, non-diagnostic progress sentence while investigating, then sends the validated spoken report sentence by sentence to Sarvam and forwards PCM chunks as received. The browser schedules each chunk immediately rather than collecting the whole reply. Progress and report synthesis are serialized; interruption cancels both current and queued speech. Diagnostic model JSON is still buffered for validation: this update does not implement streaming raw model tokens or sentence-by-sentence model claim validation.

A single latest follow-up is retained while cancellation completes or the local cooldown elapses, and is submitted automatically when eligible. Speaking again replaces that pending follow-up. Ending the conversation or cancelling clears it. Local cooldown scheduling can resubmit a request rejected before any hosted call; provider failures/rate limits are not automatically retried. The existing 60-second free-plan cooldown and three-minute connection duration still constrain conversation pace. Earlier instructions to manually retry every local cooldown are superseded by this behavior.

The updated unit suite passed 46 tests, including streamed progress before any answer exists, serialized validated speech and contained provider startup failures. Three investigation integration tests, lint, typecheck and build passed. Manual browser microphone, audible streaming and follow-up acceptance remain pending because browser automation is unavailable on this host.

The updated live synthetic gateway test passed with 30 partial captions, two telemetry calls, a validated answer, 85,800 bytes of progress audio and 24,200 bytes of report audio before deliberate disconnection. Speech end → first progress audio at server was 365 ms; first report audio at server was 3,537 ms. These are single-sample server measurements, not audible playback latency or performance guarantees. The deployed HTML matches the checked build and reports voice enabled.
